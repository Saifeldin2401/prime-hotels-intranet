# db_schema.txt is a snapshot, not a source of truth

`db_schema.txt` (repo root) is a **point-in-time dump** of the live Supabase
database (project `dhbfaclkfysqwfppuxxa`), generated by directly querying
`information_schema` / `pg_catalog` via the Supabase MCP server. It was last
regenerated on **2026-07-21**, at which point it reflected 168 tables in the
`public` schema.

It is **not authoritative** and will drift out of date again — possibly within
days, since schema changes in this project have historically been applied
directly to the live database via `apply_migration` (MCP), independent of
what gets committed to `supabase/migrations/*.sql` in this repo. Do not trust
table/column claims in `db_schema.txt` (or in this note) once they're more
than a few days old.

## Where to get current schema truth instead

1. **Query the live database directly** via the Supabase MCP tools
   (`list_tables`, `execute_sql` against `information_schema.columns`, etc.).
   This is always accurate as of the moment you run it.
2. **Read `src/types/database.generated.ts`** — a TypeScript-specific
   generated-types file kept current by `npm run db:types`. It is more
   detailed than `db_schema.txt` (full TS types, enums, function signatures)
   and should be regenerated after any schema-changing work lands.

## Local migrations do not fully match live history

As documented in `docs/prd/00_system_grounding_report.md` (§0, "Repo/Live
Drift"), as of 2026-07-21 `supabase/migrations/*.sql` in this repo does
**not** fully match the live database's applied-migration history:

- The live project has migrations applied directly via MCP `apply_migration`
  that have no corresponding file in the repo's `supabase/migrations/`
  folder (these added, among other things, an Audit/Quality module, a
  Reporting subsystem, and `expense_claims`).
- Conversely, a number of local migration files in the repo have no matching
  entry in the live migration history — either superseded by differently
  named live migrations covering the same ground, or never applied.

**Practical implication:** treat the live database (via MCP) as the source of
truth for schema questions, not local migration files, and not
`db_schema.txt` beyond its stated snapshot date. See
`docs/prd/00_system_grounding_report.md` for the full detail and reasoning.

## Regenerating db_schema.txt

There is no automated script for this yet. To refresh it, query the live DB
via the Supabase MCP tools (`list_tables` with `verbose: true`, plus
`information_schema.columns` / `pg_stat_user_tables` / `pg_tables.rowsecurity`
for row counts and RLS status) and rewrite the file, updating the "regenerated
on" date in its header. Consider wiring this into a script analogous to
`npm run db:types` so it doesn't require manual MCP queries each time.
